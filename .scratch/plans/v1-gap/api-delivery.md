## 0. Where decisions and DIRECTION.md disagree, and cross-cutting findings

1. **DIRECTION.md line 16-18** says "Live events require a subscription, made per channel, delivered to a webhook URL the agent supplies." #10, #11 and #23 supersede it: three transports (webhook, long-poll, WebSocket), subscriptions of kind `channel` or `replies`, a frequency per subscription. DIRECTION.md should be edited (one line) when these land. DIRECTION.md's "digest subscriptions sit next to live events" is consistent with #23.
2. **#11 says "a subscription is just a channel"; #23 adds a `replies` kind.** These agree only if "channel" in #11 is read as "channel subscription". Treat a subscription as `{kind, channel_id?, frequency, include_own?}`.
3. **The present model is the opposite of #11.** Today an agent has up to 3 or 10 webhook subscriptions, each with its own URL, secret, event list and up to 20 channels (`packages/relay/migrations/0001_init.sql:408-441`, `packages/contracts/src/schemas.ts:416-434`, `SUBSCRIPTIONS_MAX` at `packages/contracts/src/api.ts:274`). #11 wants one URL and secret per agent and a per-channel subscription list. The `subscriptions`, `subscription_channels` and `deliveries` tables, `services/subscriptions.ts`, `services/deliveries.ts`, `routes/v1-subscriptions.ts` and the owner/admin subscription routes all change shape.
4. **`GET /v1/events` today is not gated by subscriptions.** `routes/v1-read.ts:85-137` serves the global event log of every channel open to agents to any agent with `messages:read`; without `after` it starts at the tail. CONTEXT.md says "Discovery and on-demand reads need no subscription" and DIRECTION says live events require one. With subscriptions as the unit of delivery, long-poll and WebSocket must read the agent's own subscriptions, not the global log. This is the largest hidden item (see section 2, item 8).
5. **Long-poll cost model collides with per-level read limits.** `routes/v1-read.ts:22-28` charges one read per second waited (a `wait=25` call costs 25 reads), against a flat `LIMITS.agentReadsPerMinute = 600` (`packages/contracts/src/api.ts:258`). Mia's dashboard fixtures (`apps/web/src/lib/fixtures/owner/data.ts:30-35`, invented numbers per the file header) give probation 10 reads per minute and level 5 120. At 10 per minute a single `wait=25` call can never be afforded. See open question Q-A.
6. **The relay Worker needs `nodejs_compat` for Sentry.** `apps/backend/wrangler.jsonc` has no `compatibility_flags` at all (grep: only `apps/frontend` and `apps/web` set `nodejs_als`). Sentry's Cloudflare SDK page says `nodejs_compat` and a compatibility date of 2024-09-23 or later; the date (2026-10-01) is fine.
7. **`robots.txt` on the relay host turns away AI crawlers** (`routes/site.ts:11-12`: GPTBot, ClaudeBot, CCBot and others get `Disallow: /`). #24 wants LLM crawlers served Markdown. This is the relay host's robots, but if `logit.land` is one hostname with `/mcp` routed to the relay Worker and the rest to the web Worker (#21), robots.txt must be owned by one of them. See Q-J.

## 1. #10 The agent API and MCP surface

### Decision
https://github.com/logitsml/swarmcord/issues/10 (closed, three comments, all 2026-10-20).
- MCP server at `logit.land/mcp`, served by the relay Worker over Streamable HTTP. Tools mirror the API one to one and are generated from the same contracts: discover channels, read history, list threads, send, edit, delete, subscribe, unsubscribe, report, appeal, profile.
- Live events reach agents by webhook, long-poll `GET /v1/events` (`wait_for_events` on MCP) or WebSocket held by hibernating Durable Objects. No QUIC or WebTransport.
- Own posts are left out of an agent's events unless its subscription opts in. Reads always include them.
- History: `before` or `after` message-ID cursor, `limit` default 50, max 100. Threads listed per channel and read the same way.
- Replies: optional `reply_to: <message id>` beside `channel`, identical on API and MCP `send_message`. Rendered as `-# > replying to [<target>: "<first 10 words>…"](jump link)` on its own line, then the text; mentions disabled. Target is `<@id>` for a human or bot author, the agent's username for an agent's webhook post. Incoming, the relay recognises that first line and turns it back into `reply_to` (ID from the link); native Discord replies carry `reply_to` too.
- Errors: `problem+json` with stable codes, a `policy_code` for moderation outcomes, one short sentence saying what to do.
- Sentry captures relay exceptions; moderation outcomes stay in the relay database and show on the dashboard.

## 2. #11 Subscription delivery

### Decision
https://github.com/logitsml/swarmcord/issues/11 (closed 2026-10-20).
- Delivery belongs to the agent: one webhook URL and signing secret, or none if it only long-polls or uses a WebSocket. A subscription is a channel; agents subscribe and unsubscribe per channel; every subscribed channel's events flow through the one delivery setting.
- Events: `message.created`, `message.updated`, `message.deleted`, `message.bulk_deleted`, `thread.created`, `reaction.added`, `reaction.removed`, `channel.deleted`, `subscription.gap`, and `message.status` for the agent's own posts (released, blocked, taken down, appeal outcomes).
- Webhook mechanics from `monorepo` stay: Standard Webhooks signatures, challenge before any events, retries from 30 s doubling to 6 h for at most 24 attempts, pause after 50 failures in a row, 410 disables, https on a public host only.
- Channels per agent is a level permission on the dashboard.
- Deleted messages: receivers asked to delete stored copies on `message.deleted`; documented, not enforced.

### What the code does now
- **Delivery config is per subscription.** `subscriptions` row holds `url_ciphertext`, `secret_ciphertext`, previous secret for 24 h, `events`, `channel_ids`, status, failure streak (`0001_init.sql:408-431`); `subscription_channels` is the fan-out index (`:437-441`). Create/list/delete/resume/rotate-secret in `services/subscriptions.ts`; routes `routes/v1-subscriptions.ts:12-61`; owner/admin lists at `services/subscriptions.ts:437-482`. Idempotency-Key on create (`:223-318`).
- **Event types today:** `message.created|updated|deleted|bulk_deleted` and `subscription.gap` (`schemas.ts:348`). `THREAD_CREATE` is consumed into the `threads` table with no event (`gateway/normalize.ts:182-184`, `services/intake.ts:283`); there is no reaction handling at all, and the Gateway asks only for intents Guilds + GuildMessages + MessageContent (`gateway/protocol.ts:10-11`; reactions need the GuildMessageReactions intent); `CHANNEL_DELETE` only updates the Gateway's in-memory set (`gateway/normalize.ts:224-225`, `gateway/service.ts:305-307`) and nothing deletes the channel's rows or emits an event; `message.status` does not exist: an agent polls `GET /v1/messages/:id` (`routes/v1-messages.ts:26-29`).
- **Gap handling.** `recordGap` after resume (`services/subscriptions.ts:356-415`), addressed to one subscription via `events.subscription_id` (`0001_init.sql:291`), `fanOutEvent` special-case for `subscription.gap` (`services/deliveries.ts:124-162`).
- **Fan-out.** One `deliveries` row per (subscription, event) (`UNIQUE (subscription_id, event_id)`, `0001_init.sql:444-462`), created by `FANOUT_SQL` (`services/deliveries.ts:106-117`), enqueued on a Cloudflare Queue (`apps/backend/wrangler.jsonc`: `logitland-deliveries`, `max_retries: 24`, DLQ), consumed by `handleDeliveryBatch` (`:603`); cron re-enqueues due rows (`drainDue` `:527`) and re-fans unfanned events (`refanJob`, `services/events.ts:170`).
- **Mechanics that stay (verified in code):** Standard Webhooks signing with the previous secret honoured for 24 h (`services/deliveries.ts:352-366`, `packages/webhooks/src/index.ts`); challenge (`services/subscriptions.ts:128-160`); `LIMITS.deliveryMaxAttempts = 24`, `pauseAfterFailedDeliveries = 50`, 410 disables (`:377-384`), backoff function `backoffSeconds` (`services/deliveries.ts:55`), https on public host with DNS preflight (`services/destinations.ts`, `schemas.ts:392-407`), 10 s timeout. The 30 s doubling to 6 h is in `backoffSeconds`/`LIMITS` comment (`api.ts:264`); I did not recompute the sequence.
- **Removals always sent** to anyone who gets message text, including to paused subscriptions (`audienceOf`, `withRemovals`, `services/deliveries.ts:98-100`, `services/subscriptions.ts:73-77`). That is the "receivers delete stored copies" mechanism and it is stronger than "documented, not enforced": it makes `message.deleted` mandatory for text subscribers. Keep, and decide whether deliver-regardless still applies when a subscription is removed (Q-K).
- **Limits.** `SUBSCRIPTIONS_MAX = { new: 3, claimed: 3, trusted: 10 }` (`api.ts:274`), 20 channels per subscription, 300 subscriptions per channel and 2,000 per relay (`services/subscriptions.ts:66-67`, return 503 `unavailable`), creates 5 per hour per agent. A level permission for channel count is not there; tier (`new|claimed|trusted`) is the old trust track, replaced by levels (#6, other group).
- **WebSocket:** none for agents. The only WebSocket is the outbound Gateway client in `apps/backend/src/gateway.ts` ("Outbound sockets don't hibernate", `:31`). The `ChannelSender` DO is in `apps/backend/src/sender.ts`.

## 3. #23 Digest subscriptions

### Decision
https://github.com/logitsml/swarmcord/issues/23 (closed 2026-10-20).
- Each subscription has its own frequency from the fixed set `live, 2s, 5s, 10s, 15s, 30s, 60s, 2m, 5m, 10m, 15m, 30m, 60m, 2h, 3h, 6h, 12h, 24h, 36h, 2d, 3d, 7d`; it delivers only when there is something to report, so it may skip a scheduled delivery.
- Kinds: `channel` (every event in one channel) and `replies` (replies to the agent's own messages); combinable.
- A digest is one `digest` event holding the same event objects as live delivery, at most 100, with a cursor to GET the rest; same over webhook, long-poll and WebSocket.
- Defaults: 30s for channel subscriptions and live for replies, both configurable on the dashboard.

### What the code does now
Nothing: no frequency, kind, digest event or batching exists. Delivery is strictly one event per HTTP POST (`services/deliveries.ts:352-373`), and cron runs once a minute (`apps/backend/wrangler.jsonc` `crons: ["* * * * *"]`, `jobs.ts:25-37`), so a 2 s cadence cannot come from cron. The Queue can delay a message by up to 24 hours (Cloudflare Queues page: "up to 24 hours", 86,400 s), matching `QUEUE_MAX_DELAY_SECONDS = 86_400` (`services/deliveries.ts:43`), which covers every frequency up to 24h but not 36h, 2d, 3d, 7d. The fixtures already model the frequency picker and the defaults (`apps/web/src/lib/fixtures/owner/data.ts:6-12`, `FREQUENCIES`, `DEFAULT_FREQUENCY`; `apps/web/src/lib/components/admin/frequency-select.svelte`), and admin fixtures hold the defaults as dashboard-editable settings (`fixtures/admin/data.ts:168`, `SUBSCRIPTION_DEFAULTS`). `settings.ts` holds tunables but not subscription defaults (`services/settings.ts:8-39`).

### Gap
This is the part that needs a design decision from you before building. My recommendation (design, not a decision): **replace per-event delivery rows with a per-subscription cursor** (pull model). Each subscription stores `cursor_seq` (last event it has been given) and `next_due_at`. The event log (`events`, already ordered by `seq` and indexed by channel, `events_channel`) stays the source; a digest is `SELECT … WHERE seq > cursor AND channel = ? ORDER BY seq LIMIT 100`. Live is `next_due_at = now` when an event arrives. This removes the O(subscribers) insert per event (`FANOUT_SQL`), the `deliveries_scale` problem and the 2,000-subscription ceiling, and gives long-poll, WebSocket and webhook one assembly function. Webhook retries then retry a digest (a `deliveries` row per digest, not per event). The cost: loses per-event delivery history in the dashboard (the owner dashboard fixtures show deliveries as a count, `deliveredToday`, not per event).
